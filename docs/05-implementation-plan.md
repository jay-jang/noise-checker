# 05. 구현 계획 — 마일스톤과 담당

> 원칙: **데이터 먼저, 모델 나중.** 좋은 사전 + 빠른 매칭만으로 사고의 대부분을 막을 수 있다.
> ML/이미지/LLM은 오탐을 줄이고 커버리지를 넓히는 단계에서 붙인다.

## 마일스톤 개요

| 단계 | 기간(가늠) | 목표 | 출시 기준 |
|---|---|---|---|
| **M0 기반** | 1주 | 저장소·DB·스키마·정규화 확정 | 스키마 마이그레이션 + 정규화 속성 테스트 통과 |
| **M1 시드 사전** | 3~4주 | **실사고 기반 고위험 용어 50~100개 active** + must_pass 초판 + 수집→검수 운영 루프 가동. 나머지 후보는 draft 백로그 (교차 리뷰 합의 2 — '수량보다 사고 예방 커버리지'로 재정의. 카테고리 비대칭 유지) | active 전 항목 evidence ≥ 1·검수 완료, **검수 콘솔 MVP 가동(첫 주)**, must_pass 초판, 첫 릴리스 |
| **M2 텍스트 MVP** | 2주 | `/v1/check/text` 동기 검사 (매칭+변형) | must_catch ≥ 95%, **must_pass(revise_recommended 기준) ≥ 98%** — ambiguous 슬롯(F8/F9/F18-21)의 review_recommended 통과율은 분리 측정·보고만 하고 M3 이후 게이트화, p95 < 150ms |
| **M3 문맥 분류** | 3주 | 동음이의어 오탐 해소 (ML+LLM 폴백) | ambiguous 평가셋 F1 ≥ 0.85, 오탐률 절반 감소 |
| **M4 이미지 MVP** | 3주 | OCR + pHash 표식 매칭 | 표식 검증셋 재현율 ≥ 0.9, 실사고 이미지 케이스 통과 |
| **M5 업데이트 자동화** | 2주 | 수집기 3종+ 검수 콘솔 + 릴리스 게이트 | 주간 수집→검수→릴리스 사이클 1회 완주 |
| **M6 베타** | 2주 | batch API, 피드백 루프, 고객 파일럿 | 파일럿 고객 실데이터 평가 리포트 |

총 약 15~17주 (1인+에이전트 기준; 병렬화 시 단축 가능. M1 검수가 임계경로 — 검수 용량 계획 참조).

## 단계별 상세

### M0 — 기반 (담당: detection-engineer, pipeline-engineer)
- PostgreSQL + pgvector 도커 구성, Alembic 마이그레이션으로 `02-database-design.md` 스키마 생성
- `src/normalizer.py` 구현 + hypothesis 속성 테스트 (멱등성, 오프셋 보존, NFKC 일관성)
- `data/` JSON 스키마(jsonschema) 확정 — 이후 모든 에이전트 산출물의 계약
- CI: pytest + ruff + 마이그레이션 검증

### M1 — 시드 사전 (담당: lexicon-researcher, data-curator, pipeline-engineer(콘솔), 사람 검수)
- **첫 주: 검수 콘솔 MVP (Streamlit)** — M5에서 전진 배치 (교차 리뷰 합의 2, Critical 상향): 후보 큐 조회, 승인/반려(트랜잭션 — 승인 시 term/source/evidence/incident 생성+review_log), evidence 첨부, **라이선스 게이트 프리뷰**(active 전환 전 license_class 통과 여부 표시), 검수 체크리스트(04 §4), 원문 기본 블러 토글. 검수가 임계경로이므로 도구 없는 수작업 구간을 만들지 않는다.
- `01-research-report.md`의 소스 우선순위에 따라 적재:
  1. 실사고 사례 기반 용어 (논란 보도가 있는 것 — 최우선, evidence 자동 확보)
  2. 위키 문서 기반 커뮤니티 용어 (유래 서술 포함)
  3. 공개 데이터셋의 단어 수준 사전 (라이선스 확인 후)
- 카테고리별 커버리지 — **청정 출처 접근성에 따라 비대칭 설정** (01 §6 비대칭 확인 반영; 총량은 50~100 active — 수량 압박으로 origin_story 품질을 희생하지 않는다):
  - 고인비하/지역비하/커뮤니티은어/여혐: active 각 10~20 (실사고·언론 정착 우선, 위키백과 사건사고·MIT/Apache 사전으로 evidence 확보 용이)
  - **남혐(misandry): active 15+** (청정 origin/definition evidence 확보분 한정) + 나머지는 `draft`(needs_verification)로 적재해 M3 이후 재근거화 백로그로 이월. 남혐 전용 공수 별도 배정: 페미위키 API 수집 → 박대아(2018) 호칭형/대체형 유형론으로 골격 구성 → 항목별 청정 출처 재근거화. **evidence 기준 완화는 절대 금지** (draft 유지가 원칙).
  - 장애비하: 자원 상황(SelectStar 라벨 등)에 맞춰 10+
- **검수 용량 계획**: 검수자 1인당 일 15~25건(동음이의어·ambiguity 항목은 2배 가중) 기준으로 총 공수 산출 — 검수가 M1의 임계경로. 검수 강도 차등(04 §4: severity 5/법무 플래그만 풀 체크리스트) + LLM 사전 분석 초안(04 §3)을 '검토·수정' 방식으로 운영 + 실사고 역추출 우선 처리로 공수 절감. 필요 시 M1을 '핵심 카테고리 우선 N건' 단계로 분할.
- 검수 절차: 2인 원칙(생성자≠승인자) — 1인 운영 시 "생성 세션≠승인 세션" + 체크리스트
- **IAA(검수자 간 일치도) 측정** (교차 리뷰 A-C3): 주간 무작위 표본 10% 이중 검수 → Cohen's κ ≥ 0.7 목표, 미달 시 검수 가이드라인 보정 후 재측정. 1인 운영 구간은 2주 시차 자기 재검수(self-agreement)로 대체. severity·ambiguity·카테고리 판정의 개인 편향(특히 남혐/여혐 비대칭)이 사전에 각인되는 것을 감시하는 장치.
- **검수자 부담 완화**: 혐오 원문 연속 노출 일 2시간 상한 + 콘솔 기본 블러/펼침 토글 + 고강도 항목(고인비하 합성 등) 옵트아웃. 검수 품질 유지 조건이자 운영 지속성 장치.
- variant-engineer: 변형 규칙 v1 (자모분리, leet, 초성) + 오탐 시뮬레이션

### M2 — 텍스트 MVP (담당: detection-engineer, qa-redteam)
- 릴리스 빌더 v1 (오토마톤 컴파일 + **Kiwi 사용자 사전 자동 생성**(active 용어+verified 변형 등록 — 형태소 오분해로 경계 필터가 무력화되는 것 방지, 교차 리뷰 C-C1) + manifest) → FastAPI 검사 엔드포인트
- 형태소 경계 검사(Kiwi) + safe_contexts 1차 오탐 필터
- 골든셋 3종 구축 (M1 incident 데이터에서 must_catch 추출)
- **이 시점에 내부 도구로 즉시 사용 시작** — 실사용 피드백이 최고의 데이터

### M3 — 문맥 분류 (담당: ml-engineer)
- 동음이의어 대조 셋 구축 (용어당 50쌍; 부족분 LLM 합성+사람 검수)
- KcELECTRA 파인튜닝 → ONNX int8 → API 통합 (ambiguous 매칭에만 호출)
- 신뢰도 캘리브레이션 → mid-conf만 Claude API 폴백 (비용 상한 설정)
- 문장 수준 분류기(사전 외 위험 경고)는 공개 코퍼스로 학습, `out_of_lexicon_warning`으로만 노출

### M4 — 이미지 MVP (담당: image-engineer)
- 비동기 잡 큐 + OCR→텍스트 파이프 (가장 흔한 사고 경로 — 최우선)
- 표식 레퍼런스 수집(license_ok 확인) → pHash 인덱스 → CLIP kNN
- 손모양 감지는 M4 말 실험 기능(`experimental: true`)으로 — 정확도 검증 전 revise_recommended 금지 (상한 review + `requires_human_visual_review`)

### M5 — 업데이트 자동화 (담당: pipeline-engineer)
- 수집기: ① 뉴스 모니터(논란 키워드 검색) ② 위키 변경 감지 ③ HF/GitHub 데이터셋 갱신 감지
- 검수 콘솔 고도화 (MVP는 M1 첫 주 전진 배치됨 — 여기서는 수집기 연동 자동 큐 적재, 대량 처리 UX, 권한 분리, IAA 대시보드)
- 릴리스 게이트 자동화: 골든셋 회귀 + diff 리포트 + 승인 → 배포
- 운영 주기 확정: 뉴스 일간 / 위키 주간 / 데이터셋 월간 / 전체 사전 분기 감사

### M6 — 베타 (담당: 전원)
- batch API, 피드백 API, 사용량 계측, API 키 발급
- 파일럿: 실제 마케팅 카피 묶음으로 블라인드 평가 → FP/FN 리포트 → 사전/모델 보정

## 리스크와 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| 핵심 데이터셋 라이선스가 비-permissive(NC·ND·재배포제한·**불명**) | 시드 규모 축소 | 실사고/뉴스/위키 기반 자체 구축 경로를 주력으로, 비-permissive 데이터는 평가 전용 격리 (불명=차단 기본값) |
| **검수 병목으로 M1 지연** (검수가 실제 임계경로) | 첫 릴리스·후속 마일스톤 연쇄 지연 | 검수 강도 차등 + LLM 초안 검토 운영 + 실사고 우선 처리, M1 범위 단계 분할 가능 설계 |
| **남혐 시드의 청정 출처 열위** (최다 사고 유형인데 자원 최빈약 — 01 §6) | 균일 목표 적용 시 일정 병목 또는 evidence 기준 완화 압력 | 별도 트랙·비대칭 목표(15+)·기간으로 격리, evidence 기준 완화 절대 금지(draft 유지) |
| 동음이의어 오탐으로 신뢰 상실 | 서비스 가치 훼손 | ambiguity 플래그 + 문맥 분류를 M3에 조기 배치, revise 대신 review_recommended 상한 기본값 (03 §2 단계 4 정책표) |
| 나무위키 등 출처 변경/소실 | 근거 추적 불가 | 수집 시점 스냅샷 + archive.org 의무화 (M0부터) |
| 신조어 속도를 수집이 못 따라감 | 미탐 | 피드백 루프 + out_of_lexicon 경고 + 뉴스 일간 모니터 |
| 변형 규칙 공개로 회피 악용 | 검출력 저하 | 규칙/임계값 비공개, 응답에 매칭 내부 로직 미노출 |
| LLM 폴백 비용 폭증 | 운영비 | 신뢰도 게이트로 호출률 제한 + 일일 비용 상한 + 캐시 |

## 운영 비용 가늠 (베타 기준)

- 인프라: VM 2대(API+워커) + 관리형 PG ≈ 월 $150~300
- LLM 폴백: 호출률 5% × haiku 단가 기준 텍스트 10만 건/월 ≈ $10~30
- OCR: 자체 PaddleOCR 기본(무료), 고정밀 필요 시 클라우드 OCR 종량
