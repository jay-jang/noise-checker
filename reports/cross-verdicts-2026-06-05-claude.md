## 리뷰 B (Codex) 평가

### Critical

**B-C1. 제품이 "혐오 검출"보다 "논란 가능성 판정"에 가까운데 판정 체계가 재정의 안 됨 / `block` 명칭이 자문 포지셔닝과 충돌**
- 판정: **partial (자기 리뷰 M4와 부분 합의)**
- 근거: `block` 명칭 vs 자문 포지셔닝 긴장은 타당한 지적이며 03 §6 "risk 등급명도 단정 아닌 권고", 01 §5와 표면적으로 충돌한다(B-M7과 동일 뿌리). 다만 "판정 체계가 재정의 안 됨"은 과장이다 — 01 §5·03 §6은 이미 advisory 포지셔닝, 회색지대 `warn` 강등(03 §6), 단정 금지어를 명문화했다. `harm_likelihood`/`controversy_likelihood` 분리는 개선이지 미설계 결함이 아니다. 내 리뷰 M4(집게손가락 메타리스크)와 부분 겹침이나 B-C1은 명명 일관성, M4는 2차 가해 리스크로 초점이 다르다. → Critical보다 Major가 적정.

**B-C2. M1 "핵심 용어 300+개" 목표가 데이터 현실성·검수 병목 과소평가 → 50~100개로 낮춰라**
- 판정: **partial (자기 리뷰 C3과 운영 병목 인식 공유, 단 수치 처방은 reject)**
- 근거: 검수 병목 자체는 실재하며 05가 이미 인정한다("검수가 M1 임계경로", 05 리스크표). 그러나 "300+가 수량 압박"이라는 진단은 문서를 부분 오독했다 — 05 M1은 균일 300이 아니라 **카테고리별 비대칭 + 남혐 15+만 active, 나머지 draft 백로그**(v1 #11 반영)로 이미 완화했고, "evidence 기준 완화 절대 금지(draft 유지)"를 못박았다. 즉 "수량 압박으로 origin_story 부실화"는 이미 구조적으로 차단됨. "50~100개" 처방은 v1이 정밀하게 재정의한 비대칭 목표를 되돌리는 것. 병목 인식은 내 C3와 공유하나 C3는 검수자 신뢰성·심리·IAA로, B-C2는 수량 하향으로 갈라진다.

**B-C3. 이미지 손모양 성공 기준(M4 재현율 ≥0.9)이 지나치게 낙관적 → 손모양은 베타 기능 아닌 내부 리서치로**
- 판정: **agree (자기 리뷰 M4와 부분 합의, C-발견8과 합의)**
- 근거: 타당하다. 01 §1.E는 집게손가락이 "일반 집는 동작과 구별 불가"라고 자인하는데, 05 M4 재현율 ≥0.9는 **표식 검증셋 전체** 기준이라 손모양 FP 폭발과 정합성이 약하다. 다만 문서가 이미 방어선을 깔아둔 점은 반영해야 한다 — 05 M4는 손모양을 `experimental: true`로 격리하고 "정확도 검증 전 block 금지", 06 §2.4는 "FP율 <5% 전까지 experimental 유지"를 명시한다. 따라서 "베타 기능"이라는 전제는 다소 오독(이미 실험 격리)이나, "API에 `requires_human_visual_review`만 반환" 처방은 06 §2.4 게이트를 강화하는 방향으로 유효. C-발견8과 합의.

**B-C4. CC BY-SA 기반 상업 API의 산출물/DB 파생물 문제를 충분히 좁히지 않음 → 데이터 3계층 분리**
- 판정: **agree (자기 리뷰 C1과 강한 합의)**
- 근거: 핵심 합의 항목. 내 C1과 동일 문제(effective_license가 사실상 항상 SA로 수렴 + API 응답에 origin 요약 포함이 "배포"인지 미분석)를 지적한다. 02 §3.10, 04 §5는 추적 메커니즘만 갖췄을 뿐 "API 응답=배포 시 SA 전파가 고객에 전가되는가"라는 사업 생사 질문은 미해결이다. B의 처방(`clean_permissive_core`/`share_alike_core`/`restricted_eval_only` 3계층 + BY-SA origin_story를 응답에 직접 파생문장으로 넣지 않기)은 내 C1 개선안 2(출처 링크만 제공)와 수렴. **Top 5 확정 항목.**

### Major

**B-M1. 문맥 분류가 너무 늦다(M3) → M2를 "internal advisory alpha"로 재정의**
- 판정: **partial**
- 근거: M2가 외부 MVP로 부르기엔 미성숙하다는 지적은 일리 있으나, 05 M2는 이미 **"내부 도구로 즉시 사용 시작"**으로 명시하지 외부 베타가 아니다(외부 파일럿은 M6). 또 06 §1·05 M2는 v1 #16 반영으로 "ambiguous는 M3 전까지 block만 실패로 카운트"하여 warn 남발이 게이트를 깨지 않도록 이미 설계됨. "internal alpha" 명명은 정직성 개선이나 구조적 결함은 아님. 내 C2(캐스케이드 한계)와 인접하나 B-M1은 마일스톤 명명, C2는 도그휘슬 미스매치로 초점이 다름.

**B-M2. 한국어 NLP 리스크가 형태소 수준으로 축소 → `linguistic_features` 별도 설계**
- 판정: **agree (C-발견1과 부분 합의)**
- 근거: 03 §2는 Kiwi 형태소 경계·safe_contexts 중심이고, 담화·화용 신호(종결어미 "-노", 숫자/금액 포맷, 인용·보도 문체, 누적 노출)는 흩어져 있어 feature로 통합 설계되지 않았다. 다만 일부는 이미 존재 — composite_rule(02 §3.8)이 숫자/날짜/금액/인접을, 01 §6이 "-노 종결어미 플래그"를 다룬다. 따라서 "축소"는 과장이나 "feature 통합 설계 부재"는 유효. C-발견1(Kiwi OOV로 후속 필터 무력화)과 같은 뿌리. 내 M9(음절 내 한글 삽입 변형 누락)와도 인접.

**B-M3. 변형 회피 대응의 공격자 모델 불명확 → `known/rule/suspicious_obfuscation` 분리**
- 판정: **partial (자기 리뷰 M9와 인접)**
- 근거: "사전 키와 먼 변형엔 약하고 규칙 넓히면 FP 급증, 우선순위 기준 없음"은 타당하며 내 M9와 같은 영역이다. 다만 문서는 이미 부분 대응 — 03 §2는 "AC 후보에 한해 퍼지 + 후보 수 상한 + 조기 종료", 02 `term_variant.verified`(미검증 자동생성은 릴리스 제외), 06 §1 evasion 재현율 85%(점진 상향)로 FP/FN 균형 장치를 둔다. `suspicious_obfuscation`을 별도 신호로 반환하자는 처방은 신규 가치이나, 공격자 모델 "전무"는 과장.

**B-M4. "출처 있는 용어"와 "검출해야 할 용어"의 간극 과소평가 → `emerging_watchlist` 중간 상태**
- 판정: **partial (중복 지적 — 이미 설계됨)**
- 근거: 문제 인식(신조어는 먼저 쓰이고 나중에 언론화 → active 지연)은 타당하나, **처방이 이미 문서에 존재**한다. 02 `status`에 `draft`(근거 미확정 격리)가 있고, 04 §1 candidate_queue + 05 M1 "draft 백로그로 이월"이 사실상 watchlist 역할. 01 §6은 "회색지대 표현에 별도 위험도 점수 → 검수자 경고(자동 차단 아님)"를 명시. `emerging_watchlist`는 draft + candidate_queue의 리네이밍에 가까워 신규성이 약함. → Major보다 Minor.

**B-M5. 뉴스 기반 신규 포착은 편향된 신호원 (정치·젠더 과대표집, 오프레이밍 후보화)**
- 판정: **agree**
- 근거: 04 §2 news-monitor가 "신규 도그휘슬은 거의 항상 언론 보도로 먼저 표면화"를 전제로 두는데, B의 지적대로 보도는 이미 논란화된 사건 중심이라 조기예방엔 늦고 젠더·정치 이슈 편중 위험이 실재한다. 문서가 feedback-intake(04 §5)·trends-checker(04 §4)를 보조 신호로 두긴 하나 "뉴스=신조어 선행 신호"로 과신하는 프레이밍은 사실이다. 내 C2(신규 도그휘슬은 사후 최速 등재로만 대응)와 같은 통증점.

**B-M6. 운영 로그/프라이버시 정책(24h 파기)이 학습 전략(옵트인 클러스터링)과 충돌 → `privacy_preserving_case_packet`**
- 판정: **agree (자기 리뷰 m4와 합의)**
- 근거: 03 §7(24h 파기, 원문 미기록 해시만) vs 04 §6 ool-warning-miner(옵트인 데이터 클러스터링) + 06 §1(오탐 신고 확정 시 must_pass 자동 후보)는 실제로 긴장한다. 미탐 개선엔 원문·주변 맥락이 필요한데 보존 최소화와 충돌. 내 m4(신고 입력 24h 파기 시 골든셋 편입 불가)와 동일 충돌의 다른 단면. case_packet(span+주변 N자+해시+삭제 SLA) 처방은 m4 해법(파기 예외 명시)을 구조화한 것. 심각도는 Minor~Major 경계.

**B-M7. API 응답 예시(`overall_risk:"block"`, "제거하세요")가 법적 포지셔닝과 불일치**
- 판정: **agree (B-C1과 동일 뿌리, 자기 리뷰 M4와 인접)**
- 근거: 명확한 내부 모순이다. 03 응답 예시는 `overall_risk:"block"`, `label:"harmful"`, "제거하거나 교체하세요"를 반환하는데, 같은 문서 03 §6은 "단정 문구 응답 템플릿 금지", "risk 등급명도 권고"라고 한다. 예시와 원칙이 직접 충돌. B-C1을 Major로 내리면 B-M7과 통합되어 단일 "자문형 출력 언어 정합" 항목이 된다. **Top 5 후보.**

**B-M8. DB 스키마가 검수 상태(status)와 릴리스 정책을 충분히 분리 안 함 → `release_policy` 추가**
- 판정: **partial**
- 근거: "active=전 고객 배포 가능"이 항목별 노출 차등(텍스트/이미지 전용, 내부 전용, 법무 검토)을 못 담는다는 지적은 부분 타당. 다만 문서는 이미 일부 분리 — incident에 `disclosable`/`legal_reviewed`/`display_title`(02 §3.7), image_marker의 `experimental` 격리(05 M4), license 게이트(04 §5)가 노출을 통제한다. `release_policy` enum은 이들을 일반화하면 깔끔하나 "전혀 분리 안 됨"은 과장. → Minor~Major.

**B-M9. 실사고 incident를 회귀 테스트로 쓸 때 저작권·명예훼손 리스크가 테스트 저장소에 남음**
- 판정: **partial (자기 리뷰 m? 및 C-발견10과 인접)**
- 근거: 타당한 잔여 리스크지만 문서가 이미 상당 부분 방어 — 02 §3.7 sample_text "내부 전용·최소 인용", 02 §5 "커뮤니티 원문 장문 인용 금지". 다만 "골든셋 공개/비공개 분리, 민감 sample 암호화/private artifact, CI 분리"는 06에 명시되지 않은 실질 갭이라 신규 가치 있음. C-발견10(excerpt 길이 제약 부재)과 같은 "저작권이 테스트/스키마 레벨에서 물리적으로 강제되지 않음" 테마.

**B-M10. KcELECTRA 파인튜닝이 라이선스·편향·라벨 불일치 과소평가 → 초기 모델을 ambiguous reranker로 제한**
- 판정: **agree (자기 리뷰 M2와 강한 합의, C-발견3과도 인접)**
- 근거: 핵심 합의. 내 M2(CC BY-SA 학습 데이터의 모델 가중치 전이)와 직접 겹친다 — 01 §3이 "학습 데이터 라이선스가 모델에 전이될 수 있음"을 자인하고 학습 메인(K-MHaS·BEEP)이 전부 CC BY-SA다. 추가로 B는 **라벨 체계 불일치**(서로 다른 라벨 데이터 혼합 시 출력 의미 불명)를 짚는데, 01 §2 라벨 매핑표가 있으나 매핑 신뢰도(label mapping confidence)는 기록되지 않아 유효한 보강이다. "ambiguous reranker로 제한 + model card/provenance 기록" 처방은 내 M2(Apache/MIT만으로 1차 모델) 대안과 보완적. **Top 5 후보.**

**B-M11. 성능 목표(≤500자/≤10매치 p95)가 실제 고객 batch 워크플로우와 분리됨**
- 판정: **partial (중복 지적 — 이미 반영됨)**
- 근거: 문제 자체는 타당하나 **상당 부분 이미 반영**(v1 #9). 03 §7은 "batch API는 항목당 타임아웃+전체 데드라인+부분 결과 반환 정책 별도 정의", 06 §2.6은 "워스트케이스 시나리오 분리: 다중 매치 긴 카피, batch 묶음 각각 별도 p95"를 명시. "카피 100개 batch 5초, 이미지 20장 2분" 같은 워크플로우 단위 SLO 수치화는 신규지만, "분리되어 있다"는 진단은 v1 반영분을 부분 간과. → Minor.

**B-M12. 검수 콘솔이 핵심 제품인데 M5로 과소취급 → M1으로 올려라**
- 판정: **agree (C-발견6과 합의)**
- 근거: 강한 합의. 04 전 흐름이 사람 검수를 품질·법적 방어선으로 삼는데(04 원칙1), 검수 콘솔은 05 M5(Streamlit MVP)에 배치되어 **M1(임계경로, 300+ 검수)에선 도구가 없다**. C-발견6과 독립적으로 동일 지적. 내 C3(검수자 신뢰성)와도 연결 — 콘솔이 없으면 IAA·로테이션·근거 비교도 불가. **Top 5 확정 항목.**

**B-M13. v1 리뷰 #12 반영 불완전 — candidate_queue엔 payload JSONB만, combination_rules 검증 구조 없음**
- 판정: **agree**
- 근거: 정확한 적발. 04 §3 candidate_queue는 `payload JSONB`만 두고 04 §1 kind에 `new_marker`는 있으나 composite_rule 후보의 구조화 필드(`proposed_composite_rules`, `negative_examples`)가 없다. 02 §3.8 composite_rule은 DB엔 있으나 **수집·검수 단계에서 어떻게 생성/검토되는가**는 비어 있다. v1 #12 반영표가 "candidate 스키마 combination_rules"를 주장하나 04에서 확인 안 됨 → 실제 반영 갭. "숫자코드는 positive evidence만으로 승인 금지" 처방도 타당(오탐 위험).

**B-M14. v1 리뷰 #17 반영(variant-engineer→qa-redteam 소유권)이 제공 문서에서 확인 안 됨**
- 판정: **reject (오독 — 입력 범위 한계로 인한 오판)**
- 근거: B는 "05·06에 소유권 규칙이 안 보인다"고 하나, 06 §1 evasion 행이 출처를 "variant-engineer 규칙 + qa-redteam 능동 탐색"으로 명시하고, v1 #17 반영 위치는 **`.claude/agents/*.md`(에이전트 프로필)**이다. 내 리뷰 교차검증에서 "variant-engineer(스테이징 tests/evasion/)→qa-redteam(정본 tests/golden/evasion.jsonl 머지) 소유권이 두 에이전트 파일+06 §1에 일관 서술"을 확인했다. B가 에이전트 파일을 입력에서 누락해 "미반영"으로 오판한 것 — 실제로는 반영됨. "06에 책임자 명시" 처방은 강화로는 유효하나 "미반영" 진단은 reject.

## 리뷰 C (Antigravity) 평가

> 주의: C는 Part 1에서 v1 18건을 "18건 모두 누락 없이 매우 일관되게 반영"이라 평가했다. 그러나 B-M13이 적발했듯 #12(combination_rules의 candidate 단계)는 04에서 미확인이고, 내 교차검증도 #1·#16 등 표본만 확인했다. C의 "18건 전부 완벽 반영" 단정은 검증 깊이가 얕은 과신으로, B-M13과 모순된다.

### Critical

**C-발견1. Kiwi 형태소 분석기 의존 + 신조어/변형문 OOV로 후속 필터(음절 경계/safe_contexts) 무력화**
- 판정: **partial (부분 오독 — 이미 설계로 방어됨)**
- 근거: "Kiwi OOV가 후속 필터를 무력화한다"는 전제가 03 설계를 부분 오독했다. 03 §2 단계1은 **AC 매칭이 1차이고 Kiwi는 그 후 보조 필터**다 — "exact 매치 + unambiguous + safe_contexts 비해당이면 형태소 검사 생략"(빠른 경로)이며, 음절 경계 정렬 필터는 **Kiwi가 아니라 src_offset 기반**(02 §4.1, 03 §2)으로 동작한다. 즉 C의 개선안(자모 윈도우 우선, Kiwi는 보조)은 **이미 채택된 설계를 결함으로 오인해 재처방**한 것. 단 "active 용어를 Kiwi 사용자 사전에 동적 추가" 처방은 신규 가치(01 §3이 "사용자 사전 지원"만 언급, 빌드 자동화는 미명시). → Critical은 과대평가, Minor 수준.

**C-발견2. 남혐 lexicon 데이터 편향 + 수집 기아 (페미위키 편향, 박대아 2018 노후화)**
- 판정: **partial (중복 지적 — 핵심은 이미 반영, 일부 신규)**
- 근거: 문제 자체는 실재하나 **대부분 이미 문서에 반영**됨(v1 #11). 01 §1.A는 페미위키를 "관점 편향 → 교차검증"으로 명시 표기하고, 05 M1·리스크표는 남혐 비대칭(active 15+ & draft 백로그)·별도 트랙·"evidence 완화 금지"를 못박았다. 즉 "교차검증 없이 수용"은 문서가 이미 금지. C의 신규 기여는 ① data-curator에 "중립성 검수 가이드라인" 공식 삽입 ② 판례 사실관계 역추적을 M1 필수 소스로 — 이 둘은 유효한 운영 보강. 그러나 Critical로 올릴 만큼 미설계는 아님(내 C3 IAA 지표와 일부 수렴). → Major.

### Major

**C-발견3. KcELECTRA 파인튜닝 데이터 극소화(용어당 50쌍)로 과적합 → M3는 LLM Few-shot으로 단순화**
- 판정: **agree (B-M10·자기 리뷰 M2/M7과 인접)**
- 근거: 05 M3 "용어당 50쌍(총 100문장 내외)"으로 KcELECTRA(수천만 파라미터) 파인튜닝은 과적합 위험이 실재하며, 05이 "부족분 LLM 합성+사람 검수"로 보강하나 100문장 규모 자체가 빈약하다. "초기엔 LLM few-shot, 데이터 축적 후 KcELECTRA 전환" 처방은 합리적이며 03 §2의 LLM 폴백 인프라와 정합. B-M10(reranker 제한)과 방향 일치. 내 M7(KcELECTRA 2022 토크나이저 신조어 약점)과도 연결. 유효한 Major.

**C-발견4. 텍스트(동기)/이미지(비동기) 분리로 B2B 통합 복잡 → 통합 `POST /v1/check/campaign` + `wait_for_image`**
- 판정: **partial**
- 근거: B2B 통합 편의 지적은 제품적으로 일리 있으나, 동기/비동기 분리는 **성능 SLA를 위한 의도된 설계**다(03 §3 이미지=비동기 워커, 03 §7 이미지 p95 10s — 동기로 묶으면 텍스트 150ms 목표 붕괴). `wait_for_image=true` 블로킹 옵션은 오히려 03 §7 지연 목표와 충돌한다. 통합 캠페인 API는 편의 기능으로 타당하나 "활용성 저하"를 Major 결함으로 보긴 어렵다(이미 03 §4에 batch API 존재). → Minor.

**C-발견5. 라이선스 게이트 과도 차단으로 사전 커버리지 붕괴 → Clean Room 우회 프로세스 공식화**
- 판정: **partial (처방은 이미 존재 — 중복)**
- 근거: "NC/불명 차단으로 커버리지 협소·미탐 증가"라는 우려는 방향이 맞으나, **C가 제안한 Clean Room 우회는 이미 문서의 핵심 전략**이다. 01 §1.A 나무위키 행 "용어 존재 인지용 단서로만, 본문은 자체 재서술", 01 §7-5 "나무위키는 체크리스트로만 → 청정 출처에서 재근거화", 04 §7이 모두 동일 프로세스를 명문화했다. 즉 C-발견5의 처방은 신규가 아니라 **이미 채택된 설계의 재진술**. "미탐율 치명적 증가"도 과장 — 3중 파이프라인(01 §6)·실사고 역추출(01 §7)이 커버리지를 보전한다. → Minor(또는 기각 권고). 내 C1·B-C4와는 정반대 방향(저들은 SA 오염 축소, C는 차단 완화)이라 균형 주의.

**C-발견6. 검수 콘솔이 M5에 배치 → M1 임계경로에서 도구 없이 수작업 → M0/M1으로 앞당겨라**
- 판정: **agree (B-M12와 완전 합의)**
- 근거: 강한 독립 합의. B-M12와 동일 지적이며 근거도 정확 — 05 M1은 300+ 검수 임계경로인데 검수 콘솔은 05 M5(Streamlit). M0/M1 조기 배치 처방 타당. **Top 5 확정 항목.**

**C-발견7. 핫리로드 시 이중 버퍼 메모리 2배 팽창 + 멀티 워커 OOM 리스크**
- 판정: **agree (신규 — 자기 리뷰·B 모두 미지적)**
- 근거: 가치 있는 신규 발견. 03 §7 "이중 버퍼 로드 → 원자적 포인터 교체"는 AC 오토마톤·CLIP 인덱스·pgvector를 순간 중복 로드하므로 메모리 2배 스파이크가 실재하고, FastAPI 멀티 워커가 각자 핫리로드하면 배가된다(문서는 워커별 메모리 격리·공유 메모리를 다루지 않음). 내 M6(다중 레플리카 버전 불일치)와 같은 "다중 인스턴스 운영" 테마의 다른 단면(나는 일관성, C는 메모리). 사이드카 분리 처방은 다소 무겁지만 리스크 등재는 타당. 유효한 Major.

**C-발견8. 이미지 표식 검출 극심한 오탐 → 경고 피로 → 2차 비전 LLM 필터**
- 판정: **agree (B-C3·자기 리뷰 M4와 합의)**
- 근거: B-C3와 합의. 01 §1.E "일반 집는 동작과 구별 불가"가 근거이고, warn 남발의 경고 피로는 실재. 다만 문서가 이미 `experimental`(05 M4)·"FP<5% 전까지 experimental 유지"(06 §2.4)로 방어 중인 점은 반영해야 함. 2차 비전 LLM 필터는 유효한 고도화 처방이나, 내 M4 관점에선 **자동 필터 강화보다 "인사조치 근거 사용 금지" 고지가 우선**(필터를 강화할수록 "검출됐다"는 신뢰가 오히려 2차 가해를 키움). 처방 방향에 일부 이견.

### Minor (참고 — 지시상 Critical/Major 대상이나 한 건만 적시)
- **C-발견9**(M2 ambiguous 채점 예외를 "꼼수"로 규정): **reject**. v1 #16의 정당한 의존성 역전 해소를 "꼼수"로 폄하한 오독. 06 §1은 warn 통과율을 **분리 측정·보고**하고 M3에서 게이트화한다고 명시 — 방치가 아니다. 다만 "M2에서 safe_contexts 하드 필터 강제" 처방은 05 M2가 이미 "safe_contexts 1차 오탐 필터"로 포함하므로 중복.
