## 합의 Top 5

1. **SA/라이선스 전파 범위 미정의**: A-C1, A-M2, B-C4, B-M10이 같은 축을 지적했다. API 응답·사전 아티팩트·모델 가중치·평가 리포트별 법무 판단이 M0/M1 게이트가 되어야 한다.

2. **도그휘슬·최신 신조어 대응이 사전 중심 구조와 충돌**: A-C2, B-M1/B-M4/B-M5, C-C2가 합의한다. 제품 메시지는 “실시간 완전 차단”보다 “근거 있는 고위험 코드 + 빠른 등재/검토 루프”로 낮춰야 한다.

3. **집게손가락/이미지 표식은 기술보다 제품·윤리 리스크가 크다**: A-M4, B-C1/B-C3, C-M8이 일치한다. 손모양은 베타 API의 자동 경고 기능이 아니라 human review 보조와 강제 고지 중심이 적절하다.

4. **검수 체계가 임계경로인데 도구·독립성·일관성 설계가 부족**: A-C3, B-C2/B-M12, C-M6이 합의한다. M1부터 검수 콘솔, 2인 검토 범위, IAA/감사 로그, 검수자 부담 완화가 필요하다.

5. **문맥 분류와 위험도 정책이 늦고 불명확하다**: A-M1, B-M1/B-M7, C-M3이 교차 확인한다. `block/warn/info` 산정표와 자문형 응답 언어, ambiguous 처리 정책을 먼저 고정해야 한다.

## 기각 권고

- **C-M5의 “라이선스 게이트 때문에 커버리지 붕괴, Clean Room이 필요”**: 전면 기각은 아니지만 신규 발견으로 보긴 어렵다. 01 §1.A·§7에 나무위키를 단서로만 쓰고 청정 출처로 재근거화하는 전략이 이미 있다.

- **C-C1의 “Kiwi 실패로 1차 매칭이 무력화”**: 과장이다. 03 §2의 1차 AC는 정규화 키 기반이고 Kiwi는 잔여 후보의 경계·safe_context 보조에 가깝다. 사용자 사전 자동화 필요성은 유지하되 Critical은 아니다.

- **A-M6의 “M6 베타는 이미 다중 API 인스턴스라 바로 문제”**: 근거가 약하다. 05의 VM 2대는 API+워커일 수 있어 다중 API 레플리카라고 단정할 수 없다.

## 심각도 재조정 권고

- **A-M1 → Critical 상향**: risk 함수 미정의는 테스트 게이트, 응답 UX, 법적 포지셔닝 전체를 막는다.

- **C-C1 → Major 하향**: 한국어 NLP 리스크는 타당하지만, 문서상 Kiwi가 1차 매칭의 단일 의존점은 아니다.

- **C-M6 → Critical 상향 검토**: M1 300+ 검수와 법적 근거주의가 핵심 가치인데 검수 콘솔이 M5이면 품질·일정 리스크가 직접 발생한다.

- **A-C3 → Major 유지 또는 Critical 조건부**: 검수자 심리 부담은 중요하지만 현재 문서 리뷰 범위에서는 제품 출시 차단 조건이라기보다 운영 거버넌스 보강 항목에 가깝다. severity 5/법무 플래그를 1인 자기검토로 통과시키는 경우에는 Critical로 본다.
