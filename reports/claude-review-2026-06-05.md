요약: Critical 3건, Major 9건, Minor 5건.

## Critical

### C1. 핵심 가치제안(유래/origin_story 제공)과 핵심 라이선스 제약(나무위키 NC + 위키 SA)이 정면 충돌 — 산출물의 ShareAlike 오염이 사업모델을 잠식
- 근거: README 6행("모든 항목에 출처와 유래를 검증 가능한 형태로 붙인다" = 차별점), 01 §0.1·§5, 02 §3.10 `effective_license`("SA 파생물 1건 이상 포함 시 'CC BY-SA 4.0'"), 02 §3.2 `origin_story TEXT NOT NULL`.
- 문제: 차별화의 핵심인 `origin_story`/`meaning`의 청정 출처는 사실상 위키백과·페미위키(둘 다 **CC BY-SA**)에 집중된다(01 §1.A에서 permissive 출처는 사전 어휘 시드뿐, 유래 서술원은 모두 SA). 02 §3.10이 이미 인정하듯 "origin_story가 SA 본문에서 파생되므로 산출물에 표기 의무 전파" → 결국 **릴리스 아티팩트 전체의 effective_license가 사실상 항상 CC BY-SA로 귀결**된다. 그런데 이 서비스는 사전 아티팩트를 직접 판매/배포하는 게 아니라 API로 "리스크 의견"만 반환하는 자문 서비스다. API 응답에 origin_story 요약을 실어 보내는 것(03 §4 응답 예시 `origin.summary`)이 CC BY-SA의 "배포(distribution)"에 해당하는지, 해당한다면 **고객(API 사용자)에게 SA 전파 의무가 전가되는지**가 사업모델의 생사를 가르는데 어디에도 분석이 없다.
- 더 위험한 점: origin_story를 "사실의 재서술"로 자체 저작권화하려는 의도(01 §1.A 나무위키 행 "본문은 자체 재서술")는, 위키백과 SA 본문을 보고 쓴 파생 서술에는 통하지 않을 수 있다(2차적저작물 판단). "사실만 추출하면 저작권 없음"과 "SA 본문 재서술은 파생물"의 경계가 origin_story마다 다른데, 이를 항목 단위로 추적하는 필드가 없다(source는 있으나 "이 origin_story가 SA 본문 파생인가 vs 순수 사실 추출인가"를 구분하는 플래그 부재).
- 개선:
  1. `term`/`image_marker`에 `origin_text_provenance` enum 추가: `sa_derived`(SA 본문 재서술 — 전파 대상) / `facts_only`(날짜·기업명 등 사실만, 자체 저작) / `internal_original`(자체 작성). effective_license 계산을 evidence source가 아니라 **이 필드 기준**으로 해야 정확하다(현재는 source.license_class만 봄 → 사실추출도 SA로 과대 오염).
  2. 법무 의견서 항목으로 "API 응답에 origin 요약 포함 = 배포 행위인가"를 M0 게이트 이전 필수 확인사항으로 명문화. 만약 배포로 보면, API 응답에서 origin_story 전문 대신 **출처 링크만** 제공하는 옵션(SA 회피)을 기본값으로.
  3. effective_license가 항상 SA로 수렴한다는 현실을 직시하고, 그래도 사업이 성립하는지(B2B API 약관에 SA 고지 삽입 가능성)를 사업계획에 반영.

### C2. "사전 매칭 → 문맥 분류" 캐스케이드의 근본 한계: 최다 사고 유형(도그휘슬/회색지대)은 정의상 사전 매칭으로 안 잡힌다 — 솔루션 접근과 사고 분포의 미스매치
- 근거: 01 §0.3("실사고 최다 유형은 남혐 도그휘슬인데 데이터 최빈약"), 01 §6("도그휘슬의 부인가능성 구조"), 03 §2(파이프라인은 단계1 AC 매칭이 진입점), 03 §2 단계3("사전 매칭 0건이어도 문장 분류기가 고위험이면 경고").
- 문제: 아키텍처의 1차 방어선은 사전(lexicon) 정확 매칭이다. 그러나 집게손가락·탱크데이·"-노" 종결·523 같은 **최다·최신 사고 유형은 표면형이 일상어와 동일하거나(523, 집는 손) 매번 새 표면형으로 변형**되어 사전 매칭의 사정권 밖이다. composite_rule(02 §3.8)이 이를 부분적으로 다루지만, composite_rule도 결국 "이미 알려진 숫자/패턴"을 사람이 등재해야 작동 → 신규 도그휘슬에는 무력. 즉 **이 서비스가 가장 막아야 할 사고가 아키텍처상 가장 약한 경로(out_of_lexicon 문장 분류기 — M3에 가서야 등장, 그나마 "경고"만)로 처리**된다.
- 더 깊은 문제: 문장 분류기(KcELECTRA, 01 §3)는 2018~2021 코퍼스로 학습되며(01 §6 "학술 코퍼스 전부 2018-21"), 06 §1이 인정하듯 "2018-21 학습 모델이 구조적으로 못 잡는 유형"이 바로 신규 도그휘슬이다. 결국 신규 도그휘슬에 대해 사전도 모델도 둘 다 약하다 — 이 갭을 메우는 건 "뉴스 모니터 일간 수집 → 사람 검수 → 핫픽스"라는 **사람 의존 운영 루프뿐**인데, 이는 솔루션이 아니라 SLA 리스크다.
- 개선:
  1. 제품 메시징을 정직하게 조정: "신규 도그휘슬은 검출이 아니라 **사후 최速 등재(보도 후 24h)**로 대응" — 즉 이 서비스의 실질 가치는 "이미 알려진 코드를 빠짐없이 + 신규는 업계 평균보다 빨리"이지 "모든 신규 코드 실시간 차단"이 아님을 M0 단계 제품 정의에 못박기(현재 README/03은 실시간 검출 뉘앙스).
  2. out_of_lexicon 경고 경로를 M3가 아니라 **M2로 당기는 것 검토** — 사전 매칭이 약한 게 구조적이라면, 문장 분류기가 보조가 아니라 도그휘슬 1차 그물이어야 한다.
  3. "회색지대 위험도 점수"(01 §6)가 composite_rule만으로 충분한지 재검토: 부인가능성 높은 표현의 동시출현 밀도(예: 한 카피에 약한 신호 3개) 같은 **누적 신호 스코어링**을 위험도 공식(03 §2 단계4)에 명시. 현재 risk 공식은 개별 매치 기준이라 "약한 신호 다수"를 놓친다.

### C3. M1 시드 300+ 검수가 임계경로인데, 검수자(도메인 전문가)의 신뢰성·일관성·심리적 부담에 대한 계획이 전무 — 1인 운영 가정이 비현실적
- 근거: 05 M1("검수자 1인당 일 15~25건", "1인 운영 시 생성 세션≠승인 세션"), 04 §4("검수 권한 분리: 1인 운영 시에도 생성≠승인"), 05 리스크표("검수 병목으로 M1 지연").
- 문제: (a) 이 도메인의 검수는 일베/남혐/고인비하 **혐오 원문을 종일 읽는 작업**이다. 콘텐츠 모더레이터 PTSD는 업계 표준 리스크인데, 1인이 일 15~25건 × 수주간 이를 수행하는 계획에 **검수자 정신건강·로테이션·심리 지원**이 0줄. (b) "1인 운영 시 생성 세션 ≠ 승인 세션"은 권한 분리의 **형식만 충족하고 실질(독립적 제2 판단)은 0** — 같은 사람이 생성하고 같은 사람이 승인하면 편향 교정 효과가 없다. severity 5/법무 플래그 항목까지 1인 자기검토로 통과시키는 건 C1의 명예훼손 리스크와 직결. (c) 검수 일관성(inter-annotator agreement) 측정·관리 계획이 없어, 검수자 1인의 정치적/관점적 편향이 사전 전체에 그대로 각인된다(특히 남혐/여혐 비대칭 판정에서 치명적).
- 개선:
  1. severity 5 및 법무 플래그 항목은 **반드시 물리적으로 다른 2인** 승인을 강제(1인 운영이면 이 항목들은 외부 법무/전문가 검토 전까지 draft 고정) — 05/04의 "세션 분리" 완화 문구를 이 카테고리에 한해 철회.
  2. 검수자 부담 완화를 운영 계획에 명문화: 혐오 원문 노출 최소화 UI(블러/요약 우선), 일일 검수량 상한, 로테이션, 심리 지원. 06이 "오탐/미탐"만 테스트하고 검수자 건강은 비기능 요구에서 누락.
  3. IAA 지표 도입: 일부 항목을 중복 검수해 일치율 측정 → 사전의 관점 편향을 정량 모니터링(특히 misandry/misogyny 카테고리).

## Major

### M1. 위험도 공식 `f(severity, match_confidence, context_score, category, composite_score)`이 정의되지 않은 채 5개 마일스톤이 의존
- 근거: 03 §2 단계4("risk = f(...)"), 05 M2 출시기준(must_pass block 채점은 risk 등급에 의존).
- 문제: f()의 실제 형태(가중합? 규칙트리? 임계값?)와 각 인자→등급(block/warn/info) 매핑 규칙이 어디에도 없다. category가 왜 입력인지(고인비하면 +가중?), severity와 어떻게 결합하는지 불명. M2 게이트(block 발생 여부)가 이 미정의 함수에 전적으로 의존하므로, f()를 못 정하면 골든셋 채점 자체가 불가능.
- 개선: 02/03에 `risk_policy` 표(category×severity×ambiguity → 기본 등급, context_score/composite_score에 의한 승강 규칙)를 명시하고, 이 정책 자체를 릴리스 아티팩트에 버저닝(manifest)해 "왜 이 등급이 나왔나"를 재현 가능하게.

### M2. KcELECTRA 기반(BERT 계열) 모델 의존 — 학습 데이터 라이선스 전이 리스크가 "주의"로만 처리됨
- 근거: 01 §3("학습 데이터 라이선스가 모델에 전이될 수 있음 — CC BY-SA 계열로만 학습"), 03 §5(KcELECTRA 파인튜닝), 01 §1.C(학습 메인 K-MHaS=CC BY-SA, BEEP=CC BY-SA).
- 문제: 메인 학습셋이 전부 CC BY-SA면 **파인튜닝 모델 가중치도 SA 파생물**일 수 있고, 이를 상업 API로 서빙하는 것의 SA 의무(모델 공개?)가 미분석. C1과 같은 뿌리지만 모델 쪽은 더 모호(가중치의 라이선스 전이는 법적으로 미확립 영역). "CC BY-SA로만 학습"하면 안전한 게 아니라 **SA가 가중치로 전파될 수도** 있다.
- 개선: M3 진입 전 "모델 가중치 라이선스 전이" 법무 판단을 게이트화. 보수적으로는 Apache/MIT 데이터(HateScore Apache, Curse-detection MIT, KOTOX MIT)만으로 1차 모델을 만들고 SA 데이터는 평가 전용으로 격리하는 옵션도 검토(데이터 충분성 별도 확인 필요).

### M3. p95 150ms 목표에 ML/LLM 폴백·이미지·콜드스타트가 숨어 있고, 동기 경로에 외부 LLM API(Claude) 호출이 들어옴
- 근거: 03 §7("동기 p95 150ms 문맥분류 제외 / 500ms 포함"), 03 §2 단계3 2차("경계 사례만 LLM API(Claude) 판정"), 05 운영비("LLM 폴백 호출률 5%").
- 문제: (a) 외부 LLM API는 네트워크 왕복만 수백 ms~수 초, p99에선 타임아웃. 동기 텍스트 경로에 외부 API가 끼면 500ms 목표는 평균에서만 성립하고 꼬리 지연은 통제 불가. LLM 폴백을 동기 응답에 넣을지/비동기로 뺄지 결정이 없다. (b) "5% 호출률"은 근거 없는 가정 — ambiguous 항목 비중이 높은 마케팅 카피(인명·지명 다수)에선 폴백률이 훨씬 높을 수 있다. (c) Claude API 의존은 **외부 종속성/가용성 리스크**(01이 Perspective 종료를 의존 금지 근거로 들면서, 정작 자기 동기 경로를 외부 LLM에 의존).
- 개선: LLM 폴백을 동기 경로에서 제거하고 "1차 응답(ML까지) 즉시 반환 + LLM 정밀판정은 비동기 후속/웹훅"으로 분리하거나, 동기 유지 시 엄격한 타임아웃+폴백 실패 시 보수적 등급(warn) 디그레이드 정책 명시. 폴백률을 실측 전까지 보수적(15~20%)으로 비용 산정.

### M4. 이미지 손모양 감지의 오탐 처리는 명문화됐으나, "집게손가락 자동검출 자체가 사회적 논란을 재생산"하는 메타 리스크 미평가
- 근거: 01 §1.E("메갈리아 집게손가락 — 자동 판정 금지, 위키백과도 '음모론'"), 03 §6("의도성 미입증 표식은 warn + 반론 병기").
- 문제: 설계는 "warn까지만"으로 신중하나, **고객사가 이 warn을 근거로 디자이너를 징계·해고하는 2차 사고**(실제 르노·BBQ 등에서 발생한 사회현상)를 이 서비스가 가속할 수 있다. "집는 손 모양 검출 도구"의 존재 자체가 마녀사냥 인프라가 될 수 있는데, 약관 면책(03 §6)은 법적 책임만 다루고 **평판/윤리 리스크**는 미다룸. 이는 README의 "윤리적 목적 한정"과 긴장 관계.
- 개선: 집게손가락류 hand_sign 검출 결과는 API 응답에서 "검출"이 아니라 "이 이미지에 손 동작이 있으며 일부 커뮤니티에서 논란이 된 형태와 유사할 수 있음 — 인사조치 근거로 사용 금지" 류의 **사용 제한 고지를 응답 페이로드에 강제 삽입**. 윤리 검토를 M4 게이트로.

### M5. composite_rule의 co_occurrence/proximity가 검사 엔진 성능·복잡도에 미치는 영향 미분석
- 근거: 02 §3.8(trigger_terms 배열, proximity_window), 03 §2 단계2(조합 평가).
- 문제: co_occurrence 규칙이 늘면 "매치된 term 집합 × 규칙"의 조합 평가가 필요한데, 규칙 수 증가 시 평가 비용·룰 충돌(한 입력이 여러 composite_rule 충족) 해소 정책이 없다. proximity(OCR px 인접)는 이미지 경로지만 텍스트 proximity_window(문자 수)도 매치쌍 거리 계산이 O(매치²) 가능. p95 목표(M3)와 정합성 미검증.
- 개선: composite_rule 평가를 매치 후보가 number/common일 때만 트리거(이미 단계2에 암시)임을 보장하고, 규칙 수 상한·평가 복잡도를 06 §2.6 워스트케이스 시나리오에 추가.

### M6. 다중 레플리카 환경에서 사전 버전 불일치 — "향후 과제"로 미뤘으나 베타(M6)에 이미 문제
- 근거: 03 §7("다중 레플리카 확장 시 전 레플리카 일괄 전환은 k8s 단계 향후 과제"), 03 §7("각 요청은 진입 시 릴리스 포인터 1회 캡처").
- 문제: M6 베타는 VM 2대(API+워커, 05 운영비)로 이미 다중 인스턴스다. 핫리로드 타이밍이 인스턴스마다 다르면 동일 입력이 인스턴스에 따라 다른 release_version·다른 판정을 반환 → "왜 어제는 잡혔는데 오늘은 안 잡히나"가 인스턴스 라우팅으로 발생. 감사가능성(03 §7) 주장과 모순. "향후 과제"로 미루기엔 베타에서 바로 노출.
- 개선: 베타 단계 SLA에 "릴리스 전환 중 일시적 버전 혼재 허용 윈도우"를 명문화하거나, 응답에 release_version이 있으므로 고객 재현 시 버전 고정 조회 API 제공. 최소한 M6 리스크표에 등재.

### M7. KcELECTRA(KcELECTRA-base-v2022)는 2022 시점 모델 — 2024~26 신조어 토크나이저 커버리지 한계
- 근거: 01 §3(KcELECTRA-base-v2022 파인튜닝), 06 §1(2024-26 실사고 회귀셋).
- 문제: subword 토크나이저가 2022 어휘 기준이라 신조어("탱크데이", "노무한")가 비효율적으로 분절되어 분류 성능이 떨어진다. 정작 핵심 가치(최신 사고)와 모델 학습 시점이 어긋남. M2 데이터-우선 원칙은 이를 회피하지만, M3에서 모델이 신조어에 약하면 ambiguous 해소(오탐 감소)와 out_of_lexicon 경고(신조어 포착) 둘 다 타격.
- 개선: M3 진입 시 모델 백본 재평가 게이트(2024+ 사전학습 모델 또는 도메인 적응 추가학습), Kiwi 사용자 사전으로 토큰화를 보강한 입력 정규화 검토.

### M8. KOLD를 평가/참조용으로 쓴다고 했으나 라이선스 "명시 없음"인데 must_catch 채점 기준 후보로 등장 — 격리 일관성 허점
- 근거: 01 §1.C(KOLD "라이선스 명시 없음 ⚠️ 평가/참조용"), 06 §2.3("공개 벤치마크 KOLD/UnSmile 테스트 분할과 병행"), 04 §7(불명 자원 = 차단 기본값, KOLD를 불명 예시로 명시).
- 문제: 04 §7은 KOLD를 "라이선스 불명 → 격리·릴리스 미포함"으로 분류하면서, 06 §2.3은 KOLD를 평가 벤치마크로 사용. 평가 사용은 릴리스 포함이 아니라 허용될 수 있으나, "불명 자원은 평가 전용 격리"라는 규칙(04 게이트0 박스)과 "KOLD/UnSmile로 평가"가 정합적인지(UnSmile은 NC라 내부 평가만 가능, KOLD는 불명) — 평가 사용조차 라이선스가 막을 수 있다는 점이 불명확. 격리 자원이 평가 채점 기준이 되면 그 평가 리포트의 공개·고객 공유도 제약될 수 있다.
- 개선: "평가 전용 사용"의 허용 범위(내부 비공개 평가 OK / 리포트 외부 공유 시 제약)를 라이선스 클래스별로 06에 표로 명시. KOLD는 저장소 LICENSE 1회 확인을 M3 평가 착수 전 필수 태스크로.

### M9. 정규화 §4.5 "반복 문자 압축 안 함"과 변형 회피의 충돌 — "ㅋㅋㅋ운지" vs "운우운지" 류 누락 경로
- 근거: 02 §4.5("반복 문자 압축은 하지 않음 — 변형은 term_variant로 명시 관리"), 03 §2 단계2(skip-char 윈도우는 비한글 1~2자만).
- 문제: 보수적 정규화는 오탐엔 안전하나, "운우운지", "운ㅇ지", "운--지" 같은 음절 내 삽입/중복 변형은 term_variant에 일일이 등재해야 잡힌다(규칙엔진이 생성하더라도 조합 폭발). skip-char가 "비한글 1~2자"만 허용하므로 한글 음절 삽입("운우지")은 빠진다. 변형 공간이 사람/규칙 관리에 의존 → evasion 재현율 85%(점진 상향) 목표의 천장이 여기서 결정됨.
- 개선: evasion 셋에 음절 내 한글 삽입/중복 슬롯을 명시 추가하고, 퍼지(soynlp 자모 Levenshtein, 03 §2 단계2)가 이 경로를 어느 정도 흡수하는지 M2에서 실측. 흡수 못 하면 skip-char 윈도우를 한글 음절까지 제한적 확장하는 룰을 ambiguity='unambiguous' 고severity 항목에 한해 검토.
